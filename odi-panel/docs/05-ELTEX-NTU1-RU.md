# Подключение вместо Eltex NTU-1 и отключение после O5

Профиль **Eltex OLT** находится в разделе «Профили» рядом с Huawei OLT, ZTE OLT и пользовательским режимом. Это начальный набор настроек для стика на базе ODI SFU 240408, заменяющего мостовой терминал Eltex (исследован NTU-1 rev.C). Регистрация на Eltex OLT подтверждена на одной линии после переноса PLOAM-пароля; работа услуг ещё не подтверждена. Сам факт достижения O5 не доказывает завершение настройки услуг по OMCI.

## Результат проведённых испытаний

В исследованном подключении стик без оптики работал более суток. С оптикой он достигал O5, затем получал ONU-G Reboot и отправлял успешный ответ. Реальные перезагрузки подтверждены сбросом uptime. По предоставленному экспорту тестов, первые примерно 27–30 секунд счётчики OMCI оставались нулевыми, после чего появлялись запросы Reboot и ответы; снимок MIB не показывал созданных услуг. Штатный NTU-1 на этой же линии давал интернет.

Из этого следовало, что обнаружен явный запрос перезагрузки, но причина его отправки OLT оставалась неизвестной. Позже причину нашли: OLT проверял PLOAM-пароль (см. следующий раздел). Исправление обеих отображаемых версий Software Image не остановило цикл. Сам по себе код `0x8848` при загрузке, наличие watchdog или пустой журнал ядра не устанавливают причину. Экспорт содержит пересказ части вложений; исходные дампы этих счётчиков в релиз не включены.

## Найденная причина: PLOAM-пароль

В исследованном подключении стик с теми же GPON SN, моделью, версиями ПО и LOID, что у NTU-1, доходил до O5, а OLT сразу присылал Reboot, не задав ни одного запроса OMCI. NTU-1 на той же линии OLT сначала опрашивал и затем настраивал. Это указывало на проверку ещё до обмена OMCI.

Расхождение показала команда драйвера PON, выполненная на обоих устройствах:

```sh
diag gpon get password
```

NTU-1 отдавал `password: 0000000000`, стик отдавал пустой пароль. После того как на стике выставили те же байты, OLT перестал отправлять Reboot, и стик проработал ночь без перезагрузок.

На NTU-1 переменной `GPON_PLOAM_PASSWD` нет, поэтому значение берётся только из `diag gpon get password`. На стике пароль хранится как 20 hex-цифр, по две на байт. Десять символов `0` — это байты `0x30`:

| Где | Значение |
|---|---|
| `diag gpon get password` на NTU-1 и на стике | `0000000000` |
| `flash get GPON_PLOAM_PASSWD` на стике | `30303030303030303030` |
| `flash get GPON_PLOAM_FORMAT` на стике | `0` |
| Панель, раздел PON / ONU, формат HEX | `30303030303030303030` |
| Панель, тот же пароль в формате ASCII | `0000000000` |

Проверенное сочетание — формат `0` и `30303030303030303030`. Его удобнее ввести в режиме HEX: в режиме ASCII панель запишет те же байты, но с форматом `1`, а влияние формата на регистрацию на устройстве не проверялось. После перезагрузки сверьте `diag gpon get password` на стике со значением NTU-1.

Пароль `0000000000` относится к исследованному подключению. У другого провайдера или на другом OLT пароль может быть иным; берите его с собственного NTU-1. Дальнейшую работу услуг (VLAN, получение адреса на WAN) это исследование не подтверждает. Включайте стик, только когда NTU-1 с тем же серийным номером отключён от линии.

Для продолжения проверки предусмотрены исправленная полная запись, счётчики регистрации и **временный перехват OMCI Reboot**. Это инструмент диагностики, а не заявленное исправление совместимости с Eltex. Порядок включения и границы перехвата описаны в [руководстве полной отладки](07-FULL-DEBUG-RU.md).

## Что делает профиль

Кнопка «Eltex OLT» открывает сравнение с текущими настройками и подсказку: какие данные подключения перенести с терминала и как сверить PLOAM-пароль. Запись происходит только после выбора полей и нажатия «Применить выбранное». После применения требуется перезагрузка.

| Параметр | Значение | Назначение |
|---|---|---|
| `OMCI_OLT_MODE` | `0` | Штатный Default Mode |
| `OMCI_FAKE_OK` | `0` | Не подменять ошибки неподдерживаемых OMCI ответом OK |
| `VLAN_CFG_TYPE` | `0` | Получать правила VLAN от OLT |
| `MOD_SWVER` | `0` | Отключить мод подмены версии ПО |
| `MOD_VLAN` | `off` | Отключить локальную правку таблиц VLAN |

Значения режимов Realtek остаются прежними: `0` — стандартный, `1` — Huawei, `2` — ZTE, `3` — пользовательский. Отдельный числовой режим Eltex в закрытый OMCI-демон не добавлен. Название профиля не означает полную эмуляцию терминала Eltex.

Профиль не меняет GPON SN, PLOAM, LOID, MAC/MACKEY, Vendor ID, Equipment ID, аппаратную версию, OMCC, Traffic Management, `DEVICE_TYPE` и скорость SFP-порта. Их значения нельзя достоверно вывести только из названия терминала. Режим `Default Mode` на штатном NTU-1 служит отправной точкой; он не гарантирует одинаковое поведение двух разных версий OMCI.

## Если O5 держится около минуты

1. Сохраните конфигурацию стика. Версию и разметку flash проверьте по [инструкции установки](03-INSTALL-AND-RECOVERY-RU.md): эта сборка предназначена для базы **V1.1.8-240408 / X100SFP**, k0/k1 `0x14c000`, r0/r1 `0x274000`. Одного названия DFP-34X-2IY2 недостаточно для проверки совместимости.
2. Введите свои параметры регистрации с рабочего терминала, включая PLOAM-пароль из `diag gpon get password` (см. раздел выше); профиль Eltex их не заполняет. Примените профиль, проверьте выбранные изменения и перезагрузите стик.
3. Оставьте страницу «Диагностика PON / OMCI» открытой до обрыва. Нажмите «Прочитать таблицы OMCI» в O5, затем сохраните диагностику после обрыва. История живёт в текущей вкладке; перезагрузка страницы её очищает. Короткие переходы между опросами могут быть пропущены.
4. Сравните uptime и состояние PON. Уменьшение uptime означает перезапуск устройства. Если uptime растёт, а O5 теряется, полная перезагрузка не наблюдалась: нужна диагностика GPON/OMCI и причина отключения на стороне OLT. Это ещё не доказательство конкретной неисправности OMCI.
5. В полном снимке отображается штатный таймер перезагрузки: `0` — выключен, число — минуты от загрузки. «Не удалось прочитать» не означает нулевое значение. Панель только читает `/rebootTime.asp`; изменить таймер можно на штатной странице. Наличие такого таймера само по себе не объясняет обрыв.

Диагностика включает Ethernet UNI (ME 11), bridge port (47), VEIP (329), ONU-G (256), ONU2-G (257), MAC bridge service (45), GEM interworking (266), GEM port (268), T-CONT (262) и таблицы VLAN. Также выгружаются доступные значения `DEVICE_TYPE`, `DUAL_MGMT_MODE`, `OMCI_DBGLVL`, `OMCI_LOGFILE`. Пустая таблица или неподдерживаемый класс сами по себе не означают ошибку: они зависят от созданной OLT модели услуг.

Снимок не атомарный: PON и uptime записываются в начале и в конце сбора. Если исчерпан лимит времени, результат помечается неполным. Это чтение текущего MIB, а не перехват OMCI/PLOAM и не журнал причин деактивации OLT.

Экспорт скрывает строки с серийным номером и паролями, включая `SerialNum` в ONU-G. Перед публичной отправкой всё равно просмотрите файл: неизвестные форматы вывода заводского ПО не могут быть полностью проверены на стендовых данных. Серийные номера и пароли абонентов в репозиторий не включаются.

VLAN 109 и GEM 136 из примера другой линии к Eltex-профилю не относятся. Их нельзя переносить без данных именно этого подключения.
